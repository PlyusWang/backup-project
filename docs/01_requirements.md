## 1. 文档目的

本文定义数据备份与恢复系统要做什么、做到什么程度、怎么算做完，作为系统设计（`02_architecture.md`）、测试（`03_testing.md`）和发布（`04_release_and_demo.md`）的共同输入。它回答四个问题：

1. 系统给谁用，边界划在哪里（第 2 节）；
2. 功能上必须做什么、哪些算加分项，每条现在处于什么状态（第 3 节）；
3. 除了"有功能"还要满足哪些质量约束，靠什么证据说明满足（第 4 节）；
4. 用户实际怎么操作，失败时会发生什么（第 5、6 节）。

编号约定：

- 功能需求用 `FR-1xx`（MUST）、`FR-2xx`（SHOULD）、`FR-3xx`（STRETCH）、`FR-4xx`（项目自定约束）。编号分配后不回收。
- 非功能需求用 `NFR-01` 起。
- 用例用 `UC-01` 起。`UC-01`～`UC-07` 沿用 `docs/requirements/use_case_description.md` 与 `docs/uml/use_case.mdj` 里已有的编号和名称；`UC-08` 起是本轮为网络与管理面补的。
- 测试证据直接引用脚本里已有的用例编号（`BR` / `ER` / `PATH` / `META` / `ARC` / `NOCMP` / `FIL` / `PRV` / `INC` / `CLI` / `SEC` / `SYM` / `UNSUP` / `US` / `RB` 等），不另造一套，这样需求、用例、测试能对上号。

状态口径：

| --- | --- |

## 2. 系统范围

### 2.1 参与者

| 参与者 | 是谁 | 入口 | 能做什么 |
| --- | --- | --- | --- |
| 本地用户 | 在装有本软件的 Linux 机器上备份自己数据的人 | `backupctl`（产品 CLI）；桌面 GUI（Qt 6） | 配置备份仓库；备份、还原、筛选预览、删除本地快照；配置并运行定时备份与实时备份；输入加密口令 |
| 远程用户 | 把备份放到远端服务器（自托管或官方云端）的同一批人 | `backupctl remote ...`；GUI「远程备份」页 | 注册、登录；把本地备份上传成完整快照或增量链；列出、下载、按依赖链还原、删除；注销自己的账户 |
| 服务器管理员 | 运行备份服务器的人 | SSH 登录服务器本机后使用 `backup-server-admin`、`backup-server-keygen`、`backup-cert-tool`、`scripts/backup-server-admin.sh` | 查看服务状态、用户列表、某个用户的快照、存储概览；在服务已停止的前提下删除用户或快照；生成服务器身份密钥、签发与检查证书 |

三个参与者处在三种信任位置，不能互相合并：

- 管理能力只存在于服务器本机，不走 BPNET1，也没有对外的管理端口；协议里没有管理员操作码。
- 远程用户能且只能操作自己账户下的数据：磁盘路径由服务端用数字 user id 生成，客户端给的用户名和显示名一次都不参与路径拼接；删除也永远作用在 token 所属的 user id 上。
- 本地用户与服务器管理员之间没有共享凭据：服务器身份用 X25519 公钥 / 指纹（pin 模式）或离线根签发的证书（证书模式）验证，账户口令只用于账户认证。

### 2.2 边界

**在范围内**：本地备份与还原、快照仓库管理、文件筛选与预览、打包、压缩、加密、桌面 GUI、定时备份、实时备份、特殊文件类型、增量备份与依赖链还原、远端存储、远端用户管理、云端元数据管理、传输加密、发布打包。

**不在范围内**（不是漏做，是当前版本的明确边界，逐条见 3.6 节）：

- 块级增量（只做文件级：以内容摘要判断变化，按文件粒度保存 delta）；
- 传输级断点续传（会话可以 RESUME，但一次失败的上传不会被自动重发，见 FR-302）；
- ACL、xattr、atime、ctime 的保存；
- socket 作为可恢复对象；
- 过滤表达式语言（NOT、括号、正则、按内容搜索、保存的过滤器预设）；
- 管理员的图形管理端；
- Windows / macOS 客户端：构建、脚本、uid / gid / inode / 设备号语义都按 Linux 写，目标平台是 Ubuntu 24.04 LTS + GCC + C++17。

### 2.3 两条贯穿全系统的约束

**核心与前端解耦。** 业务逻辑在纯 C++17 的核心里（`src/`、`include/`），产品 CLI、Qt Widgets GUI、Qt Quick/QML GUI 三者共用同一份核心，没有"CLI 一套、GUI 再写一套"的路径。`make` 默认只构建 CLI 与服务器命令行，GUI 是显式的 `make gui` / `make gui-modern`。筛选规则语法、备份选项组合、时间周期解析、字节数格式化这些容易分叉的判定，都只有一个实现（`Filter::AddRule`、`IsSupportedBackupOptionCombination`、`ParseBoundedScheduleNumber`、`FormatByteSize`），前端只负责把结果翻译成界面文案。

**秘密不进命令行。** 备份 / 恢复口令只从 `/dev/tty` 读（CLI）或从界面输入框读（GUI），不接受命令行参数、环境变量或管道输入；`remote` 子命令没有 `--password`。唯一例外是自动测试用的 `BACKUP_REMOTE_PASSWORD`，它只读不打印。口令不写配置、不写日志、不进归档。

补充说明（几条容易读错的边界）：

- **归档命名权在程序手里。** 产品 CLI 没有"把备份写到任意路径"的参数：归档一律落在配置好的仓库里、由程序命名。旧版的直连路径（调用方自己给归档路径）现在只存在于测试夹具 `tests/tools/archive_cli.cpp` 中，用于覆盖归档格式与旧格式兼容，不再是产品能力。
- **无变化不产生快照。** 定时路径用上一份成功快照的强 manifest（每个普通文件的内容摘要）与当前源比较，相同就跳过，既不调用备份引擎、也不产生 `.bak`、也不动 manifest。`schedule run` 是"忽略时间表立即检查"，**不是**强制备份。
- **加密的现实边界。** AES-256-CTR + HMAC-SHA256 是本项目能给出的最强组合；DES-CBC 只有 56 位有效密钥强度，明确标为教学 / 兼容用途。两者都是课程项目的手写实现，没有经过外部密码学审计，这是设计上写死的说明，不是"以后再说"。
- **定时与实时只在其 runner 运行期间生效。** GUI 开着、或 `schedule watch` / `realtime watch` 在前台跑着，计划才会被评估；关掉程序就不会触发。程序本身不 daemonize、不安装系统服务。

### 3.3 SHOULD

| 编号 | 需求 | 状态 | 入口与主要实现 | 验证 |
| --- | --- | --- | --- | --- |
| FR-201 | 特殊文件类型的备份与还原：软链接、硬链接、FIFO、字符设备、块设备 | 已实现 | 归档类型 3～7（`EntryType`）；硬链接按 `(st_dev, st_ino)` 只存一份 payload，其余条目记归档内首个路径；恢复用 `symlink()` / `link()` / `mkfifo()` / `mknod()`；三种打包方式都能表达这五类 | UNSUP-01～UNSUP-04、META 区、`ustar_test.sh` |

边界与理由：

- **socket 不进归档。** 归档格式里没有 socket 类型。遇到会进入备份集合的 socket，整次备份明确失败——静默跳过、跟随它、当成普通文件复制这三种做法都会让"备份成功"变成假话。只有用户用规则**显式排除**它时才跳过（`ShouldSkipSpecialEntry`）。
- **设备节点需要权限。** 归档精确保存 uid / gid / major / minor；非 root 进程恢复字符或块设备时 `mknod()` 会失败，此时给出的是明确错误并说明需要 `CAP_MKNOD`，而不是悄悄跳过。
- **ownership 尽力而为。** 归档里存的是数字 uid / gid 加解析出来的名字。恢复属主需要特权：root 能精确还原，非 root 会被拒绝，此时恢复继续完成其余部分，并在 `RestoreReport.skipped_ownership` 里如实计数、在输出里说明，不假装完整恢复。
- **USTAR 的表达边界。** name 100 / prefix 155 / linkname 100 字节，uid / gid / size 用八进制字段；装不下就明确拒绝，不截断。GNU tar 生成的 ustar 归档可以被本产品的恢复路径读取，这条互操作有测试固定。

补充说明：

- **远端只做存储后端。** 服务端不实现 Filter、打包、压缩、加密、增量或恢复引擎：它把客户端送来的字节当成"有名字、有长度、有 SHA-256 的不透明数据"存起来，校验长度与摘要后原子发布。真正的格式判断与恢复永远在客户端（或本地产品核心）里做。
- **远端元数据只用来定位，不用来信任。** 下载下来的每个字节都要过 SHA-256（下载路径 → 材料包成员 → 归档自己的 payload 验证），解包后还要用 `LoadVerifiedSnapshotIdentity` 确认"这份文件就是那个 snapshot_id"。服务端说"这是 R2 的父"不算数，归档自己的信封说了才算。
- **远端缓存里没有凭据。** 缓存目录只放三件套，不存口令、token 或服务端私钥；删掉它最多让下一次备份重新下载一遍链。

## 4. 非功能需求

本节的要求都能落到具体的代码约束或自动化测试上。引用的数字来自脚本最近一次完整运行（`scripts/final_gate.sh` 的日志与质量证据目录）；本次重写文档没有重新执行测试。

### NFR-01 正确性：Round-Trip 必须逐字节成立

对声明支持的内容形态，必须满足 `Restore(Backup(Data)) == Data`，对声明支持的元数据必须恢复到原值。判定不是"命令返回 0"，而是三件事同时成立：`diff -r` 结构一致、逐文件 `cmp` 字节一致、全树 `sha256` 一致。`scripts/test.sh` 的 A 区（`BR-01`～`BR-10`）覆盖空文件、空目录、2 MiB 随机二进制、UTF-8 中文内容与中文路径、带空格的文件名、多级目录；ARC-01～ARC-14 覆盖更多内容形态。质量套件的维度 3 连续做 10 轮 backup → restore，每轮都做全树比对。`NOCMP-01`～`NOCMP-04` 反过来证明 payload 是原样写入的、没有被压缩或编码。

增量路径的正确性判定是"应用完整条链之后，源树的 manifest digest 等于目标 delta 声明的 `current_manifest_digest`"（INC 区），不是"恢复命令没报错"。

### NFR-02 元数据正确性

元数据要求在 META-00～META-11 里逐项覆盖：mode（含 setuid / setgid / sticky）、uid / gid、mtime 秒 + 纳秒、目录结构、空目录。两条实现约束保证了结果：一是恢复收尾顺序固定为 ownership → mode → mtime（写文件内容会改 mtime，所以时间戳必须最后写）；二是目录 metadata 按深度从深到浅恢复、root 目录最后（创建子项会改父目录的 mtime）。做不到的部分必须报告而不是吞掉：非 root 恢复属主失败时计入 `RestoreReport.skipped_ownership` 并输出说明。

### NFR-03 失败必须可见，且不留半成品

任何失败路径都不允许出现"命令失败但磁盘上留着一个看起来可用的归档 / 目标目录 / 临时文件"。要求的落地方式是：

- 恢复两阶段执行：先把归档完整 preflight 一遍（magic、版本、header、路径、payload 边界、条目数、重复路径与父子关系、文件尾），全部通过才动磁盘；
- 备份写唯一临时文件，成功后原子发布；失败删掉自己创建的半成品；
- 恢复先写兄弟暂存目录，metadata 全部收尾后才 rename 成目标；
- 测试约定里，"被拒绝"的用例必须同时断言没有留下任何文件。

覆盖这些路径的是 ER 区（错误输入）、BAD-00～BAD-21（损坏归档只能 fail closed，含截断、位翻转、非法 header）、PATH / PTH 区（路径拓扑）、SYM 区（写侧与读侧路径规则必须对称）、UNSUP 区（不支持的条目类型）。失败用例还要求不能是被信号打死的（退出码 ≥ 128 直接算失败）。

### NFR-04 崩溃一致性与幂等

配置、状态、归档、marker 的保存一律是"唯一临时文件 + fsync + rename + 目录 fsync"，读者看不到半个文件。定时路径的顺序固定为"先发布归档、再落 manifest、再淘汰、最后落 state"，并且 manifest 自己带着归属（属于哪份快照、哪个仓库、哪个源目录），只有与 state 记录完全一致才允许由"manifest 相同"推出"可以跳过"；文件丢失、损坏或换了仓库，结论一律是"没有可信基线"——重建一份完整基线，绝不漏掉变化。重复执行是幂等的：没有变化就不产生新快照。

### NFR-05 易用性

- CLI 的用法错误（未知选项、缺少值、重复的单值选项、越界数字）与业务失败分开：用法错误退出 2，业务失败退出 1，成功 0，另一个实例在跑 3。脚本因此能区分"参数写错了"和"环境不允许"。
- 错误信息直接来自核心的原文（`std::string* error_message`），界面不做二次包装、也不吞掉；不认识的输入明确报错，不静默取默认值。
- 界面不显示还没实现的功能：定时页与实时页的加密项直接写"暂不支持"，而不是给一个点了没反应的开关。
- 预览会如实报告截断：最多列出 300 条，超过时明确说明"还有条目没进窗口"，而且遍历是按真实备份的完整规则走完的——不能为了快在第 300 项停下，把第 301 项上的 socket 或权限错误漏掉。
- 危险操作有确认：GUI 注销账户要求重新输入当前口令并逐字输入账户名；`remote delete-account` 要求 `--confirm <用户名>`。
- GUI 忙碌期间把相关输入与按钮一起禁用（`modern_gui_check.sh` 断言同时禁用的处数），避免"点了没反应"。

### NFR-06 可维护性

- 单一语义来源：筛选语法只在 `Filter::AddRule` 裁决；备份选项组合真值表只在 `IsSupportedBackupMode`；周期数字解析只在 `ParseBoundedScheduleNumber`；字节数格式化只在 `FormatByteSize`；应用默认路径只在 `app_paths.h`；uid / gid 名字解析只在 `user_directory`。前端不实现第二套。
- 分层清楚：业务逻辑不依赖 Qt（`src/`、`include/` 是纯 C++17），GUI 只做桥接；服务器源文件列表是显式的，不链接备份引擎。
- 编码规范：Google C++ Style + clang-format 检查（`scripts/lint.sh` 退出码 0）；编译选项 `-std=c++17 -Wall -Wextra -Wpedantic`，当前从零构建 0 警告。
- 注释率与行宽：产品源码 183 个文件、91438 行物理行，注释行占 21.40%（`scripts/comment_ratio.py`，含行内注释不计入分子），超过课程基线 `≥ 20%` 的内部目标；按显示宽度计算（中文按 2 列）的超 80 列"可处理行"为 0（`scripts/source_style_check.py`）。

### NFR-07 安全边界（本地）

- 仓库项的名字必须是单组件、非空、不是 `.` / `..`、不含分隔符与内嵌 NUL、以 `.bak` 结尾；仓库本身与列表项都用 `lstat` 判断，软链接不会被列出、解析或删除。
- 归档不能落在源目录内部；实时备份在启用阶段按 `realpath` 之后的路径组件比较 source 与 repository，两者相等或互相包含都拒绝（不能按字符串前缀比较，`/home/a` 与 `/home/abc` 没有祖孙关系）。
- 边界说清楚：这些检查覆盖普通使用场景下的路径越界，**不保证**仓库祖先路径组件里没有软链接，也不消除检查与使用之间的 TOCTOU 竞态；需要更强隔离时应把校验与使用绑到同一个目录句柄上。这条限制写在 `backup_catalog.h` 里，不假装已经解决。

### NFR-08 安全边界（远端与传输）

- 口令存储：PBKDF2-HMAC-SHA256 + 每用户随机 salt + 迭代下限 200000；不存明文、不存单次 SHA-256、不用固定 salt；校验用定长比较。
- 会话：无状态 HMAC token，12 小时有效期；token 的签名只证明"这是服务端签发的"，不证明账户还在，所以每个会碰数据的操作都要回查账户是否存在（注销后旧 token 仍然签名有效，必须被拒）。
- 登录节流：按用户名字符串计数（对不存在的名字也限速，否则限速本身成了"这个用户名存在吗"的探针），连续 5 次失败锁 60 秒，成功一次清零。
- 错误面收敛：服务端只回协议里定义的错误码，不把 `errno` 或绝对路径发给客户端——那本身就是目录结构泄漏；内部原因只写服务端日志。
- 身份与密钥：服务器身份私钥是 32 字节 X25519 标量，写文件用 `O_NOFOLLOW` + 0600 + 普通文件校验；token 密钥放在 600 的 `secrets.env`，只读、不打印。客户端不做 TOFU：没有配置 pin 或可信根就直接拒绝连接。
- 不降级：要求 BPSEC2 的服务端收到 BPSEC1 的 ClientHello 即以"拒绝降级"失败，握手失败不退回明文 BPNET1。
- 服务端默认只监听 127.0.0.1；要监听公网地址必须同时满足"配置了证书"和"给出一句话理由"（理由写进启动日志），默认行为是 fail closed。
- 数据目录独占：服务端启动时在 `<root>/.backup-server.lock` 上抢 flock 并持有到退出；管理工具做破坏性操作前必须先拿到同一把锁。这是内核持有的锁，进程崩溃会自动释放，不留假死状态。

### NFR-09 可测试性与可复现

每个可独立验证的层都有脚本入口：功能（`scripts/test.sh`）、质量四维度（`scripts/quality_test.sh`）、静态检查（`lint.sh`、`modern_gui_check.sh`、`source_style_check.py`、`comment_ratio.py`）、各模块单测（压缩、加密、归档、Filter、目录、计划、实时、网络、证书等），由 `scripts/final_gate.sh` 串成 49 个入口统一跑。当前一次完整运行中 49 个入口全部 exit=0（含 build、sanitize-build、gui-rebuild 三行与 46 个套件），`failed suites = 0`；`scripts/test.sh` 自报 `PASS=279 FAIL=0`，质量套件 66 项通过，`scripts/modern_gui_check.sh` 通过 692 项、失败 0 项。

测试用到的故障注入都显式命名（`*ForTesting` / `Inject*ForTesting`），产品路径里没有任何地方调用它们；需要造真实失败（权限、`ENOSPC`、磁盘写失败、事务失败）才能覆盖的分支，走的是这些接缝加纯函数，而不是靠不可复现的竞态。

### NFR-10 资源边界

- 压缩、上传、下载、恢复都是流式的：峰值内存与输入规模无关（Huffman 只要 256 个频次与固定 I/O 缓冲；LZSS 要 32 KiB 窗口加 261 字节前瞻，外加一个私有临时文件）。
- 协议与格式的所有长度字段先过上限再谈分配：单帧 payload ≤ 1 MiB，单条流 ≤ 4 TiB（显然不合理的拦截），单个材料包成员 ≤ 16 GiB，delta 信封 ≤ 8 MiB，tombstone 与条目数各有上限。协议里不存在"声明长度是 2^64-1 就去 resize"的路径。
- 服务端的并发是有界的：固定 worker 池，最大并发客户端数 = worker 数，不生成 detached 线程；数据库访问用一把互斥锁加 busy timeout 串行化。
- 传输有整体时间预算：握手可以设总超时，避免"每个超时周期挤一个字节"的对端把连接永远占住。

### NFR-11 构建与交付

## 6. 关键用例详述

### UC-01 数据备份

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-01 |
| 用例名称 | 数据备份 |
| 参与者 | 本地用户 |
| 前置条件 | 系统已配置备份仓库（不存在时由程序创建）；源路径存在、是真实目录；用户对该目录有读权限、对仓库有写权限 |
| 触发器 | 用户在 CLI 或 GUI 上发起一次备份 |
| 成功结束状态 | 仓库里出现一份新的快照（完整快照或 delta），文件内容与声明支持的元数据已写入；增量路径下若源未变化则不产生新快照，并如实报告"没有变化" |
| 失败结束状态 | 返回具体原因，磁盘上不留下可被误认为成功备份的半成品 |

**基本流程**

1. 用户配置仓库（`config repository set` 或 GUI「设置」页保存仓库路径）。
2. 用户选择源目录。
3. 用户可选地输入筛选规则、打包 / 压缩 / 加密选项和策略（`full` 或 `incremental`）。
4. 系统在动手之前做选项组合校验：本版本会拒绝的组合（增量 + USTAR、增量 + 加密；自动触发路径另加一条"不能加密"）直接报错，不静默降级成别的策略。
5. 系统用 `lstat` 扫描源树（不跟随软链接），产出 DFS 先序、顺序确定的条目表；硬链接按 `(st_dev, st_ino)` 只保留一份 payload。
6. Filter 决定条目是否进入备份：exclude 优先，存在 include 时普通文件必须命中至少一条，命中 exclude 的目录整体剪枝。
7. 系统按 打包 → 压缩 → 加密 生成 v2 容器，写入仓库里的唯一临时文件，成功后原子发布成 `<源目录名>_YYYYMMDD_HHMMSS.bak`（重名依次试 `_001`～`_999`）。
8. 完整策略：写出一份自包含快照，并落 `.manifest` 与 `.identity` 副文件。增量策略：没有可信基线时先建完整基线；有变化时写 delta；没有变化时什么都不写。
9. 系统返回归档文件名、变化摘要与它实际做了什么（`full` / `delta` / `no changes`）。

**异常流程**

- 源路径不存在或不是目录：立即失败，不创建任何输出。
- 仓库未配置：提示"先运行 `config repository set <path>`"，不做任何猜测。
- 归档路径落在源目录内部（例如仓库就在被备份的目录里）：在创建输出之前失败。
- 源树里有 socket 且没有被规则显式排除：整次备份失败，并说明原因。
- 打包期间普通文件的大小或 mtime 发生变化，或写 payload 后算出的内容摘要与 manifest 不一致：整次失败并删除半成品。
- 加密选项已选但没有拿到口令（终端不可用、用户取消）：失败，不产出未加密的"替代品"。
- 磁盘写入失败、路径过长、`opendir` / `readdir` / `lstat` 出错：fail closed，返回具体路径与 errno 描述。

### UC-02 数据恢复

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-02 |
| 用例名称 | 数据恢复 |
| 参与者 | 本地用户 |
| 前置条件 | 仓库里存在目标快照；目标目录不存在或为空目录；加密归档需要正确的口令 |
| 触发器 | 用户选择一份快照与目标目录并发起恢复 |
| 成功结束状态 | 目录树、文件内容与声明支持的元数据恢复完成；增量目标由依赖链还原到该还原点的状态 |
| 失败结束状态 | 返回具体原因，目标目录不出现；preflight 未通过时不创建任何东西 |

**基本流程**

1. 用户在仓库列表里选择一份快照（必须是单组件 `.bak` 文件名），或直接在 CLI 里给出文件名。
2. 用户选择目标目录。
3. 系统按 magic 识别文件种类：v2 容器 / 旧版 v0.1 归档 / `BKPINC1` delta（不看扩展名）。
4. 完整快照：解码并校验 160 字节容器 header，再校验"磁盘上实际 payload 字节的 SHA-256 等于 header 声明的值"（这一步不需要口令）。
5. 若归档是加密的：从 `/dev/tty`（CLI）或输入框（GUI）取口令，用 PBKDF2 派生密钥，先验证 HMAC，再解密。
6. delta：解析依赖链（父必须存在、身份必须等于子节点记录的父身份、必须同属一个 generation、深度不超过 64），先恢复 base，再逐个 delta 应用：先按深度优先删 tombstone，再覆盖新增 / 修改 / 类型变化，最后校正受影响目录的 metadata。
7. 系统把结果写进目标目录的兄弟暂存目录，逐条流式恢复内容；软链接 / FIFO / 设备用对应原语重建。
8. metadata 收尾：ownership → mode → mtime，目录按深度从深到浅、root 最后。
9. 全部成功后把暂存目录 rename 成目标目录，返回恢复条目数与诊断（例如跳过的 ownership 数量）。

**异常流程**

- 归档不存在、不是普通文件、或是仓库里的软链接：失败。
- magic / 版本 / 保留字段 / 路径 / payload 边界 / 条目数 / 文件尾任何一项不合法：preflight 失败，目标目录保持不变。
- payload 字节与声明摘要不符（截断、位翻转、被替换）：判为"归档已损坏"，这一判定与口令无关。
- 口令错误，或容器头本身被改动：HMAC 失败。这两者在密码学上不可区分，因此界面文案是"恢复密码错误，或备份完整性校验失败"，不宣称"一定是密码错"。
- 目标目录已存在且非空：拒绝覆盖。
- 增量目标缺少父快照、链上身份对不上、出现环、超过深度上限：明确拒绝，不尝试"尽力恢复"。
- 独立的一个 delta 被当成普通归档恢复：明确拒绝，并说明它属于某条依赖链。

### UC-04 设置备份密码

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-04 |
| 用例名称 | 设置备份密码 |
| 参与者 | 本地用户 |
| 前置条件 | 用户已选择需要加密的备份选项，或恢复一份加密归档 |
| 触发器 | 备份流程请求口令，或用户在恢复对话框里输入口令 |
| 成功结束状态 | 口令用于本次派生与认证；操作完成后进程内不再保留 |
| 失败结束状态 | 口令为空或长度非法时拒绝继续；口令错误时不产出任何结果 |

**基本流程**

1. 用户在备份选项里选择 `aes-256-ctr-hmac-sha256` 或 `des-cbc-hmac-sha256`。
2. CLI 从 `/dev/tty` 读取口令（不回显、不落盘）；GUI 在输入框里读取。
3. 系统用随机 salt 与 200000 轮 PBKDF2 派生 64 字节，按算法切成加密密钥与 HMAC 密钥。
4. 加密采用 Encrypt-then-MAC：先加密、再对"归一化 header + 密文"算 HMAC，认证标签写进容器头。
5. 恢复时按同一顺序反着来：先验证 HMAC，通过后才解密；验证失败不交出任何明文字节。

**异常流程**

- 备份选了加密但口令为空：明确失败，不做"空密码也能加密"这种自欺欺人的事。
- 命令行里出现 `--password` 之类的参数：是用法错误（该参数不存在）。
- 恢复时口令错误：HMAC 验证失败，返回"密码错误或完整性校验失败"。
- 选择 DES-CBC：允许使用，但界面与文档都标明它只有 56 位有效密钥强度、属于教学 / 兼容用途。

### UC-06 定时备份

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-06 |
| 用例名称 | 定时备份 |
| 参与者 | 本地用户（触发者是系统内部的计时器，不是 Actor） |
| 前置条件 | 计划已配置并启用；仓库与源目录都存在且是真实目录；有一个 runner（GUI 或 `schedule watch`）正在运行 |
| 触发器 | 到达 `next_run` 时间；或用户点"立即检查并运行" |
| 成功结束状态 | 有变化时仓库里多出一份新快照，state 与 history 已更新；没有变化时报告"跳过（无变化）"且不产生任何文件 |
| 失败结束状态 | 记录本次失败原因与时间，下一轮照常再试；配置本身非法时进入明确的 config-error 状态并停止周期重试 |

**基本流程**

1. 用户配置计划：源目录、周期（1～525600 分钟，界面按 分钟 / 小时 / 天 / 周 输入）、保留份数（1～1000）、策略、打包 / 压缩方式、筛选规则；加密固定为 `none`。
2. 用户启用计划。系统校验源、仓库、规则与选项组合；首次启用把 `next_run` 推到一个完整周期之后（`next_run = now + interval`），不会勾上就立刻跑一次。
3. runner 按 tick 评估：先判断是否到点，未到点直接返回。
4. 到点后扫描源树，与上一份成功快照的强 manifest 比较内容摘要（目录仅有 mtime 变化不算变化）。
5. 没有变化：什么都不写，更新 `next_run`，history 记一条"跳过"。
6. 有变化：按策略创建完整快照或 delta（增量路径下若基线不可信，则重建一份完整基线并如实说明原因）。
7. 落盘顺序：先原子发布归档，再写 manifest，再做 retention，最后写 state；retention 只淘汰本 scheduler 自己创建、且没有活着的后代的快照，可见还原点依赖的祖先会被保留并计数。
8. 记录本轮结果与变化摘要到 history（最多 32 条），计算下一个 `next_run`。

**异常流程**

- 计划未启用：不写盘、不动 `next_run`。
- 配置本身不合法（读得懂结构但业务规则不认）：一个字节都不写，`next_run` 原地不动，不记 history，进入明确的 config-error 状态，直到用户显式保存一份合法配置。
- 上一份 manifest 丢失、损坏，或仓库 / 源目录已经被换掉，或记录的那份快照已被删除：判为"没有可信基线"，这一轮重建一份完整基线快照（报告为 baseline reset），**绝不**因为"manifest 恰好相同"而误判成没变化。
- 新快照创建成功但旧快照淘汰失败：报告为"备份成功，但淘汰失败"，两者分开，不把成功说成失败，也不隐瞒淘汰没做成。
- 另一个实例已经在运行：在进入任何业务逻辑之前就被应用单实例锁拒绝（退出码 3）。

### UC-07 实时备份

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-07 |
| 用例名称 | 实时备份 |
| 参与者 | 本地用户（触发者是文件系统事件，不是 Actor） |
| 前置条件 | 实时配置已保存并启用；源目录存在且不是软链接；源与仓库不重叠；`realtime watch` 或 GUI 在运行 |
| 触发器 | 被监听目录发生 create / modify / close_write / attrib / delete / move 等事件并稳定下来 |
| 成功结束状态 | 一次事件批次对应一份新快照（或"有效集合没变"的结论），并写入属于该快照的 marker |
| 失败结束状态 | 监听失败时不假装健康，清理已建立的 watch 并报出具体 errno；备份失败时记录原因，等下一批事件 |

**基本流程**

1. 用户配置实时任务：源目录、响应延迟（100～60000 ms）、最长等待（500～300000 ms，且不小于响应延迟）、保留份数、策略、打包 / 压缩、筛选规则；加密固定为 `none`。
2. 用户启用。系统校验源与仓库不重叠（按 `realpath` 之后的路径组件比较）、源是真实目录、规则语法正确。
3. watcher 递归建立 inotify watch（只用 `lstat`，不跟随软链接目录）；建立失败时清理半成品并报 errno，不返回一个"健康但什么都没监听"的实例。
4. 事件到达后进入 debounce 状态机：第一次事件确定软截止（`t0 + debounce`）与硬截止（`t0 + max_wait`），后续事件把软截止推后但不越过硬截止；持续写入因此最迟在一个 max_wait 内形成一个检查点。
5. 一批事件稳定后触发一次：Full 策略走备份引擎，Incremental 策略走增量引擎；有效集合没变就不写。
6. 每份由实时任务产生的快照会写一个 `<快照>.realtime` marker（`BPREALTIME1`），里面绑定的是**验证过的实际归档字节**身份，而不是 header 的声明值。
7. retention 只淘汰与本任务 identity 相同的实时快照，且仍然遵守"有后代不删、读不出来不删"。

**异常流程**

- 源目录与仓库互相包含或相同：启用阶段直接拒绝——否则备份自己写出的 `.bak` 会变成下一次触发的事件，形成自己喂养自己的循环。
- 事件队列溢出（`IN_Q_OVERFLOW`）：事件历史已经不可信，触发一次 resync（重新观察当前源树），而不是按残缺的事件做增量。
- 目录结构变化（目录创建 / 删除 / 移动，或 self 事件）：整体重建 watch set，且必须先成功建立新的 fd 再关旧的，不允许出现"旧的拆了、新的没建起来"的空窗。
- 源根丢失（被删除、被移动、被卸载）：报告为明确的失败 / 降级状态，不继续假装在监听。
- marker 写入失败（归档已经成功）：不执行破坏性的实时 retention，快照退化成一份普通快照并在界面上给出告警。
- 建立 watch 时遇到 `ENOSPC` / `EACCES` 等错误：可见失败 + 清理半成品；测试通过注入 errno 覆盖这些路径。

### UC-08 远端备份

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-08 |
| 用例名称 | 远端备份 |
| 参与者 | 远程用户 |
| 前置条件 | 已配置服务器端点与身份信任方式（官方云端 / 自托管 / SSH 隧道）；通道握手成功；账户已注册且登录成功 |
| 触发器 | 用户把一份本地快照或一个源目录上传到服务器 |
| 成功结束状态 | 服务器上出现一份快照，返回 snapshot id、类型与 generation；增量续链时父关系已经登记 |
| 失败结束状态 | 返回可读原因；服务端不留下半个对象，本地不留下临时文件 |

**基本流程**

1. 用户选择服务器。CLI 侧两种来源：官方云端（地址、端口、期望 `server_id` 与内置信任根都编译在客户端里，加 `--official-cloud` 即可，用户零配置）、显式给端点（`--host` / `--port` 加 `--server-key` 指纹，或 `--identity-mode certificate --trusted-roots --expected-server-id`）。GUI 的「远程备份」页把连接方式分成 `official` / `direct` / `ssh` 三种：`ssh` 由程序自己建立并回收隧道（本机自动端口 → SSH 主机 → 服务器），`direct` 要求用户自己保证服务器可达。
2. 客户端建立 BPSEC1 / BPSEC2 加密通道：校验服务端身份（pin 比对或证书验签 + `server_id` + 有效期），派生会话密钥；任一步失败即断开，不回退明文。
3. 用户注册或登录（口令来自 `/dev/tty` 或界面输入框）；服务端校验口令、按失败次数节流，返回 12 小时有效的 token。
4. 用户选择"上传已有归档"或"备份某个目录到远端"。后者在本地按完整流水线生成快照：允许续链时取远端链头作父做增量，否则建立完整基线。
5. 客户端把三件套（`.bak` / `.manifest` / `.identity`）按 `BPSNAP1` 装进一个材料包，先流式算出整包 SHA-256。
6. 发送 `UPLOAD_BEGIN`（显示名、声明长度、声明 SHA-256、类型、父 id、lineage）；服务端在此校验父存在、同 lineage、线性链约束，并定下本次上传要登记的链关系（generation 由服务端按父推导）。
7. 按 256 KiB 分块发送 `UPLOAD_CHUNK`；服务端流式写入临时文件并同步计算 SHA-256。
8. 发送 `UPLOAD_END`；服务端核对长度与摘要，成功则原子发布到 `<root>/users/<user-id>/<snapshot-id>.bak` 并写入元数据行，返回 snapshot id、类型、generation 与父 id。
9. 客户端报告结果：这次上传的是完整基线还是 delta、上传了多少字节、是否发生了"基线重建"。

**异常流程**

- 没有配置 pin 或可信根：客户端拒绝连接（明确报"未配置服务端身份"），不做首次连接自动信任。
- 服务端身份与期望不符、证书签名验不过、`server_id` 不匹配、证书过期、证书公钥与握手中的身份公钥不同：全部明确失败并分类报告，不退回 pin 模式、不退回明文。
- 要求 BPSEC2 的服务端收到 BPSEC1 握手：以"拒绝降级"失败。
- 连接因空闲超时或隧道重启断开：下一次请求自动重连并用 token 恢复会话（`RESUME`），用户不会因此被登出；token 真的失效时才要求重新登录。
- 上传过程中本地源文件被截短或读取出错：客户端关闭连接（服务端据此删掉临时文件），保留 token；这次上传不会被自动重发，用户需要重新发起。
- 上传体积超过服务端 `--max-upload-bytes`（默认 8 GiB）：服务端明确拒绝。
- 父快照已被删除、lineage 不同、generation 不是父 + 1、父已经有活着的孩子（本产品是线性链）、代数超过 64：服务端返回链冲突错误码，客户端把它如实翻译成"这是依赖链的问题"。

### UC-09 远端快照下载与还原

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-09 |
| 用例名称 | 远端快照下载与还原 |
| 参与者 | 远程用户 |
| 前置条件 | 已登录；目标快照存在于该账户下；本地有足够空间与写权限 |
| 触发器 | 用户选择一份远端快照并指定还原目标，或只是把它下载到本地 |
| 成功结束状态 | 目标目录被还原成该还原点的内容与元数据；本地已验证缓存里留下可复用的三件套 |
| 失败结束状态 | 返回可读原因；目标目录不出现；下载与缓存只留下验证通过的产物 |

分两条路，恢复机制不是同一套：

- **产品级备份链成员**（lineage 非空）：按依赖链还原。
- **原始归档**（lineage 为空，例如用户手工上传的一个 `.bak`）：没有链、没有副文件，按本地归档格式单独恢复。

**基本流程（链还原）**

1. 用户选择一份快照并发起还原（`backupctl remote restore <快照ID> <目标目录>`，或 GUI 远程备份页）。
2. 客户端列出该账户的快照，解析目标快照的依赖链：base 在前、目标在最后，并校验每一跳的类型与 generation 自洽（full 必须是根且 generation 为 0，之后每跳恰好 +1）。
3. 逐个下载材料包到本地已验证缓存；每个成员都校验长度与 SHA-256；材料包缺成员、多成员、或者成员内容与包内声明不符都拒绝。
4. 对本地缓存里的归档调用 `LoadVerifiedSnapshotIdentity`：只有"磁盘上的实际 payload 字节"与归档自己声明的摘要一致、且两个副文件与磁盘事实逐项对上，这份快照才算可信身份。
5. 从 base 开始逐跳应用（与本地增量恢复同一份实现），写进目标目录的兄弟暂存目录。
6. 全部成功之后原子发布成目标目录，报告链长度、下载字节数、复用字节数与恢复条目数。

**基本流程（原始归档还原）**

1. 用户选择一份 `.bak`，指定目标目录。下载前**不**先问口令（大多数归档并没有加密）。
2. 客户端下载并校验服务端声明的 SHA-256，然后**按内容**识别格式（不看文件名、不看扩展名）。
3. 如果不是本产品认识的归档、或者是一个单独的 delta、或者是版本不支持的容器：明确失败并说明原因。
4. 如果是加密归档：核心明确回报"需要密码"，界面此时才要求输入口令，并用**同一份已经下载并校验过的字节**重试，不重新下载。
5. 恢复交给本地恢复核心完成，与 `backupctl restore`、GUI 本地恢复是同一条路径。

**异常流程**

- 链上某个成员已经被删除、或者父身份与子节点记录不符：解析阶段就失败，不做"尽力而为"的部分恢复。
- 链太长（含超过 64 个 delta）：拒绝恢复，并说明超出引擎上界。
- 缓存里的文件与预期身份不符、副文件被改动：这份快照不可信，拒绝用它当基线或链成员。
- 下载校验失败：只删掉自己的临时文件，不破坏已有目标文件。
- 单独一个 delta、随机文件被改名成 `.bak`、版本不支持的容器：都在"按内容识别"这一步被拒绝。
- 口令错误或归档完整性问题：返回"密码错误，或完整性校验失败"，不宣称一定是口令错；界面保持这次交互的工作副本，让用户用同一份字节再试一次。
- 目标目录已存在且非空、或不可写：拒绝，且不留下半个目标目录。

### UC-11 账户注销

| 项目 | 内容 |
| --- | --- |
| 用例标识 | UC-11 |
| 用例名称 | 账户注销 |
| 参与者 | 远程用户 |
| 前置条件 | 已登录（持有有效 token）；用户知道当前口令 |
| 触发器 | 用户明确要求注销账户 |
| 成功结束状态 | 该账户与其全部云端备份被永久删除；本机会话立即失效 |
| 失败结束状态 | 口令不正确，或服务端删除过程中失败：账户与数据保持可用（或在隔离区里，元数据仍然存在），错误原因如实返回 |

**基本流程**

1. 用户发起注销。GUI 要求重新输入当前口令并逐字输入当前账户名；CLI 要求 `--confirm <用户名>`，口令从 `/dev/tty` 读。
2. 客户端发送 `DELETE_ACCOUNT`，载荷只有当前口令——请求里没有用户名，目标永远是 token 自己所属的 user id，客户端无法指定删别人。
3. 服务端先重新校验当前口令（一个被捡到的 token 不足以删掉账户）。
4. 服务端把该账户的数据目录整体 rename 到隔离区（`<root>/trash/account-<id>.<随机>.deleted`）：这一步是原子的，做完之后这些字节对任何客户端都不再可见。
5. 服务端在**一个事务**里删除 snapshots 行与 users 行，并写一条墓碑（保证 user id 永不重用）。
6. 事务成功后才物理删除隔离目录；这一步失败只记告警。
7. 客户端成功后立即丢弃本机 token；连接仍可用于注册或登录其它账户。

**异常流程**

- 口令不正确：服务端拒绝，数据与元数据一个字节都不动，本机会话保持。
- 事务失败：把隔离目录改回原名，账户数据完好如初，返回失败。
- 事务成功但物理清理失败：只记告警——数据已经在隔离区、元数据已经不存在，不会出现"账户没了、blob 还挂在正常位置"这种半成功状态；隔离区残留由管理员在服务器本机处理。
- 注销之后再拿旧 token 发请求：token 的签名虽然仍然有效，但每个会碰数据的操作都会回查账户是否存在，因此被明确拒绝（`UNAUTHORIZED`）。
- 新账户不会复用已注销的 user id：墓碑保证了这一点，否则一个注销前签发的 token 会命中新注册的账户。

| §13.1～§13.4 网络四项 | 本地稳定后再做，作为 STRETCH | 全部落地：BPNET1 协议、账户体系、SQLite 云端元数据、BPSEC1/BPSEC2 传输加密；服务端只做"存储后端 + 传输边界" | 网络功能没有把打包 / 压缩 / 加密 / 增量搬到服务端重写一遍——那样会产生第二套实现，也会让服务端成为攻击面更大的组件 |

| §12.1 特殊文件类型 | 支持软链接、硬链接、FIFO、字符设备、块设备；socket 原则上不作为备份恢复目标 | 五类都实现；socket 进入备份集合即整次失败，只有被规则显式排除才跳过 | "原则上不作为目标"落成一条可执行的规则：静默跳过会让"备份成功"变成假话，跟随它或当普通文件复制则会造出错误的备份内容 |

### 7.2 基线之外新增的需求

这些不是课程要求，是项目在实现与自测过程中自己加上的约束，作用是让失败可见、让语义不漂移：

- **预览与"预览等于备份"的不变量**（FR-111）：GUI 与 CLI 共用同一份预览核心，预览的 included 集合必须等于同一组规则下真实备份的条目集合；预览窗口只限制展示条数，遍历规则与真实备份完全一致。
- **备份模式矩阵的前置校验**（FR-142）：把"选增量却按全量跑"这类静默降级堵在保存配置之前，代价是四个入口必须问同一个函数。
- **全产品单实例锁**（FR-401）：GUI 与 CLI 共用一把锁，锁路径与仓库、配置文件路径无关，避免"带不同参数启动"成为绕过手段。
- **无人值守不加密、增量不支持加密与 USTAR**（FR-402）：拒绝的理由是产品语义没有闭环——无人值守没有安全的持久密钥来源；增量 delta 的外层信封（父绑定与 tombstone 列表）是明文，内层容器的 HMAC 覆盖不到它，接受加密 delta 等于接受一组未经认证的路径指令。
- **远端材料包**（FR-305）：远端存的是三件套而不是单个 `.bak`，否则收到的链在副文件验证这一步必然失败。
- **SSH 隧道连接方式**（FR-304 的部署配套）：服务端默认只监听回环地址，GUI 提供"本机自动端口 → SSH 主机 → 服务器"的连接方式，由程序自己建立与回收隧道。
- **登录失败节流与账户注销的隔离顺序**（FR-302 / UC-11）：前者防止口令在线爆破，后者保证"删账户"不会留下"用户没了、数据还在"的中间态。
