## 1. 文档目的

本文用于明确数据备份与恢复系统在 Sprint 1、Sprint 2 收口时的需求边界，并作为后续系统设计、UML、测试和 Sprint 迭代的共同依据。

当前课程开发采用 Scrum / Kanban 混合方式。需求以用户目标为中心，内部实现步骤（扫描、打包、元数据写入等）不单独提升为用户用例，而在系统设计和顺序图中表达。

## 2. 系统范围

### 2.1 当前已实现范围

Sprint 1+2 已形成完整本地闭环：

```text
本地用户
   │
   ├─ CLI
   ├─ Qt Widgets GUI
   └─ Qt Quick / QML GUI
        │
        ▼
   BackupEngine
        │
        ├─ Backup → ArchiveWriter
        └─ Restore → ArchiveReader
                    │
                    ▼
              Linux / POSIX
```

当前备份结果为一个独立的 `.bak` 归档文件，使用项目自定义 Archive Format v0.1。归档 payload 原样保存，不做压缩、加密或编码。

当前保存和恢复的基础元数据：

- 相对路径；
- 条目类型（普通文件 / 目录）；
- mode 的 `0777` 权限位；
- `mtime` 秒与纳秒；
- 普通文件大小。

当前明确不支持：

- symlink；
- FIFO；
- socket；
- 设备文件；
- UID / GID；
- ACL / xattr；
- 压缩；
- 加密；
- 定时 / 实时；
- 网络备份。

### 2.2 后续规划范围

总体规划用例图中可继续保留下列未来能力，但它们不属于 Sprint 1+2 已实现范围：

- 配置文件过滤；
- 设置备份密码；
- 定时备份；
- 实时备份；
- 查看备份状态；
- 查看备份历史；
- 压缩 / 解压；
- 加密 / 解密；
- 高级文件类型和元数据；
- 网络与增量备份。

## 3. 参与者

当前系统外部参与者只有：

- **本地用户**：发起备份、恢复、查看帮助，并在后续版本中配置过滤、密码和自动备份。

`BackupEngine`、`ArchiveWriter`、`ArchiveReader`、`FileSystem` 属于已实现的系统内部组件，Scheduler、Watcher 等属于后续规划模块，它们都不作为 Actor。

## 5. 非功能需求

### 5.1 正确性

对当前声明支持的数据类型，应满足：

```text
Restore(Backup(Data)) == Data
```

对于当前声明支持的元数据，应恢复到原值：

```text
mode
mtime
directory structure
file content
```

### 5.2 健壮性

系统应对下列情况明确失败，而不是崩溃或错误报告成功：

- 源路径不存在；
- 源不是目录；
- 归档路径为空；
- 归档文件已经存在；
- 归档路径与源目录形成危险父子关系；
- 归档损坏或格式不合法；
- 恢复目标已存在且非空；
- 权限不足；
- 短读 / 半写 / `EINTR`；
- unsupported special file；
- 打包期间普通文件大小或 mtime 发生变化。

### 5.3 易用性

- CLI 参数和错误信息应明确；
- GUI 中“源目录”“备份文件”“恢复目录”的含义必须清晰；
- GUI 不显示尚未实现的虚假功能；
- 备份/恢复失败时应给出可理解错误信息。

### 5.4 可维护性

- CLI 与两套 GUI 共用同一 `BackupEngine`；
- 二进制归档细节由 Archive 模块负责，不散落在 UI 或 `BackupEngine`；
- POSIX 文件系统原语集中在 FileSystem / Archive 模块；
- UML、需求和架构文档应随真实代码演进更新；
- 自动测试应可重复执行。

## 7. UC-01 数据备份

| 项目 | 内容 |
|---|---|
| 用例标识 | UC-01 |
| 用例名称 | 数据备份 |
| 参与者 | 本地用户 |
| 触发器 | 用户选择源目录和备份文件路径并发起备份 |
| 前置条件 | 源目录存在且可访问；备份文件路径有效 |
| 成功结束状态 | 生成合法 Archive v0.1 `.bak` 文件；文件内容和受支持元数据已写入 |
| 失败结束状态 | 操作失败并返回原因；不应留下可被误认为成功备份的半成品归档 |

### 基本流程

1. 用户选择源目录。
2. 用户选择备份文件路径。
3. 系统检查源路径类型。
4. 系统确认备份文件不等于源目录且不位于源目录内部。
5. 系统确认目标归档文件尚不存在。
6. 系统按需创建归档父目录。
7. 系统写入 Archive v0.1 全局 Header。
8. 系统递归扫描源目录。
9. 对普通目录写入目录 Entry 和 mode / mtime。
10. 对普通文件写入 Entry Header、相对路径、mode / mtime、大小和原始 payload。
11. 系统回填 `entry_count` 并关闭归档。
12. 系统向用户返回成功。

### 异常流程

- 源路径不存在或不是目录：立即失败。
- 备份文件位于源目录内部：在创建输出前失败。
- 备份文件已经存在：拒绝覆盖。
- 遇到 symlink / FIFO / socket / 设备文件：当前版本整次备份失败。
- 普通文件在读取期间大小或 mtime 改变：失败并删除半成品归档。
- 写盘失败：返回具体错误，并尽量删除未完成归档。

## 8. UC-02 数据恢复

| 项目 | 内容 |
|---|---|
| 用例标识 | UC-02 |
| 用例名称 | 数据恢复 |
| 参与者 | 本地用户 |
| 触发器 | 用户选择备份文件和恢复目录并发起恢复 |
| 前置条件 | 备份文件存在且为普通文件 |
| 成功结束状态 | 目录树、文件内容以及受支持的 mode / mtime 恢复完成 |
| 失败结束状态 | 返回明确错误；若 preflight 未通过，目标目录保持不变 |

### 基本流程

1. 用户选择备份文件。
2. 用户选择恢复目录。
3. 系统确认备份文件存在且为普通文件。
4. ArchiveReader 打开归档。
5. 系统执行完整 preflight：
   - magic；
   - version / flags / header size；
   - entry header；
   - path；
   - payload 边界；
   - entry count；
   - 重复路径 / 父子结构；
   - 文件尾。
6. preflight 成功后，系统确认恢复目标不存在或为空目录。
7. 系统以可写 staging 权限创建目录结构。
8. 系统流式恢复普通文件 payload。
9. 文件写完并关闭后恢复 mode / mtime。
10. 所有子项完成后，目录 metadata 按“从深到浅、root 最后”的顺序恢复。
11. 系统向用户返回成功。

### 异常流程

- 备份文件不存在或不是普通文件：失败。
- 归档 magic / header / entry / path / payload 等不合法：preflight 失败，不创建目标。
- 恢复目标已存在且非空：拒绝覆盖。
- 磁盘写入、权限或目录创建失败：返回发生错误的路径和原因。

## 9. Sprint 1+2 验收条件

Sprint 1+2 收口至少应满足：

- CLI backup / restore 可运行；
- 单文件 `.bak` round-trip 成功；
- 普通文件、目录、空文件、空目录可恢复；
- 二进制内容 byte-for-byte 一致；
- mode / mtime 恢复；
- 危险路径拓扑被拒绝；
- 损坏归档 preflight 被拒绝；
- 两套 GUI 均能调用同一核心完成备份/恢复；
- 自动测试、lint、sanitizer 已有可重复证据；
- UML 与系统设计文档对应当前真实实现。

---

## 10. 需求变更原则

后续 Sprint 增加 Filter、Compression、Crypto、Scheduler、Watcher 等模块时：

1. 先确认用户级需求是否变化；
2. 再更新需求文档和总体用例图；
3. 内部模块变化主要更新架构、类图、构件图和顺序图；
4. 不提前把规划能力写成已实现；
5. 需求变更应保留 Git / PR 记录。
