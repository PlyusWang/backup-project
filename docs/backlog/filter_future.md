# Filter 后续问题与设计 Backlog

> 定位：记录 Filter 相关的**技术债、设计问题、暂缓功能、待决策事项**。
> 使用方式与语法见 `docs/filter_usage.md`；本文只记"现在没做、以后要解决"。
> PR #9 只实现基础筛选，本文列出的能力**都不在 PR #9 范围内**。

每项统一记录：当前状态 / 为什么 PR #9 不做 / 后续可能怎么做 / 依赖什么前置工作 /
是否影响现有格式、API 或 GUI。

## 1. 完整布尔表达式

- **当前状态**：未实现。PR #9 只有"多条 include / exclude 规则"，规则之间是 OR；
  单条规则内部可以写多个子句（隐式 AND），但没有 NOT、没有括号。
- **为什么 PR #9 不做**：布尔表达式需要真正的 parser（词法、优先级、结合性、错误位置），
  一旦引入就要长期维护语法兼容性；而备份场景里 90% 的需求是"排除若干目录、只留若干扩展名"。
- **后续可能怎么做**：给规则值加条件语法（`name:*.log AND size:>1MB` 这类），或直接做表达式引擎。
  需要决定：优先级、`NOT` 的作用域、"没有 include 就是全包含"这条默认语义如何与表达式共存。
- **依赖**：先稳定现有规则模型与匹配语义（本文其余条目的前提）。
- **影响面**：CLI 参数解析、Filter API、两套 GUI 的规则输入控件；**不影响归档格式**。

## 2. Regex

- **当前状态**：未实现；`regex:name:` / `regex:path:` / `regex:content:` 都不支持。
- **为什么 PR #9 不做**：regex 是另一个语义系统（回溯、性能、错误处理），与 glob 混用会让"为什么这个文件被排除"
  变得难以解释；而且备份工具里一次误匹配的代价很高。
- **后续可能怎么做**：用 `std::regex`（ECMAScript）先做实验，评估是否需要换成 RE2 之类无回溯实现。
- **需要额外决定**：恶意复杂正则（灾难性回溯）如何限制、超大目录扫描时的性能预算、大小写敏感策略。
- **影响面**：Filter 内部新增匹配器；不影响归档格式。

## 3. 高级匹配 modifier

- **当前状态**：未实现 `case:`、`diacritics:`、`ignore-punctuation:`、`ignore-whitespace:`、
  `prefix:`、`suffix:`、`whole:`、`whole-words:`、`start-with:`、`end-with:`、`no-...`。
- **为什么 PR #9 不做**：这些都是"匹配模式"的变体，需要一套 modifier 组合规则；在 Linux 上大小写敏感是默认且符合直觉。
- **后续可能怎么做**：把 modifier 设计成规则前缀（`case:insensitive name:*.LOG`），并定义 modifier 与 glob 的交互。
- **依赖**：跨平台 Unicode 归一化策略（见第 13 条）。
- **影响面**：Filter 语法与文档；不影响归档格式。

## 4. 内容筛选

- **当前状态**：未实现 `content:`、`binary:`、`hex:`。
- **为什么 PR #9 不做**：内容筛选必须读文件内容，会把"元数据决策"变成 I/O 密集型扫描，
  与 Filter 现在的"只看 lstat 信息"定位冲突；还要处理取消、进度、缓存与扫描顺序。
- **后续可能怎么做**：单独一层 `ContentFilter`，明确标注"会额外读取文件"，并支持用户取消与进度回调。
- **依赖**：核心需要进度 / 取消机制（当前 BackupEngine 还没有）。
- **影响面**：Filter 的一次性决策模型（需要流式回调）、GUI 的进度显示；不影响归档格式。

## 5. 高级文件属性

- **当前状态**：未实现 owner / uid / gid / ACL / xattr / hard-link count / size-on-disk /
  allocation-size / Windows attributes / reparse point。
- **为什么 PR #9 不做**：这些字段平台差异大，而且 v0.1 归档格式本身**不保存** uid/gid/ACL/xattr，
  "按 owner 筛选"在恢复端也没有对应信息。
- **后续可能怎么做**：先扩展归档元数据（如果确实要保留这些属性），再让 Filter 读同样的字段。
- **依赖**：Archive Format 的元数据扩展（需要 version 提升）。
- **影响面**：归档格式、Filter、测试。

## 6. 文档 / 图片 / 音频 / 视频元数据

- **当前状态**：未实现 EXIF、图片宽高、ISO、音频 artist/album/bitrate、视频 frame rate、
  文档 author/page count、可执行文件 version/signature 等。
- **为什么 PR #9 不做**：需要逐格式解析库（libexif、taglib、ffprobe 等），
  会让一个"本地备份工具"背上一堆第三方依赖；解析不可信文件本身也是攻击面。
- **后续可能怎么做**：做成可选编译单元（`ENABLE_MEDIA_METADATA`），解析失败只当作"无该字段"。
- **依赖**：依赖管理策略与安全评审。
- **影响面**：构建系统、Filter、文档。

## 7. Hash / Signature Filter

- **当前状态**：未实现 `crc:` / `md5:` / `sha1:` / `sha256:` / `file-signature:`。
- **为什么 PR #9 不做**：算 hash 要读全文（同内容筛选的 I/O 问题）；而且它与未来的
  **归档完整性校验**、**去重**职责重叠，先做容易出现两套 hash 语义。
- **后续可能怎么做**：先定义"归档完整性校验"（Archive v0.2 的 checksum 字段），再让 Filter 复用同一套 hash 设施。
- **依赖**：完整性校验设计、可能的第三方 hash 实现（或自写 SHA-256）。
- **影响面**：归档格式、Filter、性能模型。

## 8. child / descendant 查询

- **当前状态**：未实现 `child:`、`child-file:`、`child-folder:`、`descendant:`、
  `descendant-file:`、`descendant-folder:`、`child-count:`、`descendant-count:`。
- **为什么 PR #9 不做**：这类规则要求"先看后代，再决定父目录"，会**改变扫描模型**：
  现在的实现是单趟 DFS、边扫边写，决策只依赖当前节点的 lstat。
- **后续可能怎么做**：两阶段扫描（先建索引再决策），或者对目录延迟决定（先记下、扫描完子树再落盘）。
  两者都会影响流式写入与内存占用。
- **依赖**：扫描模型改造 + 内存预算评估。
- **影响面**：ArchiveWriter 的写入流程、Filter 接口、性能。

## 9. parent / ancestor / depth

- **当前状态**：未实现 `parent:`、`ancestor:`、`depth:`、`parent-count:`。
- **为什么 PR #9 不做**：大多数需求可以用 `path:` + `*` / `?` / `**` 表达（例如"某目录下的文件"）。
- **后续可能怎么做**：`depth:` 最容易（只需要数 `/` 个数），可以作为第一批补充；
  `parent:` / `ancestor:` 需要匹配祖先链，语义要先讨论清楚（匹配任意一级还是全部）。
- **影响面**：Filter 规则集；不影响归档格式。

## 10. 过滤后的空目录

- **当前状态**：PR #9 的既定行为是——**目录本身没被 exclude 时，即使内部文件全被 filter 掉，该目录仍会留在归档里**
  （作为结构项）。这样可以保证"只 include `*.cpp` 也不会丢掉父目录结构"。
- **为什么现在不改**：自动删除空目录会让"为什么这个目录没了"难以解释，也可能与用户预期相反。
- **后续可能怎么做**：新增显式开关 `drop-empty-directories`（默认关闭），并在文档里写清与 include 的交互。
- **依赖**：需要一次"事后遍历归档条目"的能力（当前写入是流式的）。
- **影响面**：写入流程、CLI/GUI 选项、文档。

## 11. 保存 Filter / Rule Preset

- **当前状态**：未实现规则集命名、保存、复用；也没有"源码备份 / 照片备份 / 排除构建产物"这类预设。
- **为什么 PR #9 不做**：涉及配置文件格式、用户级与项目级配置的优先级、GUI 管理界面、导入导出，
  是独立的一块功能，和"筛选语义"本身可以分开。
- **后续可能怎么做**：定义一个小配置文件（例如 `filters.toml` 或 JSON），规则就是现在这套字符串；
  GUI 提供 preset 下拉框与"另存为预设"。
- **依赖**：配置读写层（当前只有 QSettings 级别的偏好设置）。
- **影响面**：CLI/GUI、文档；不影响归档格式。

## 12. Macro

- **当前状态**：未实现 `image:`、`audio:`、`video:`、`source:` 以及用户自定义 macro。
- **为什么 PR #9 不做**：macro 本质是"规则集的别名"，应该建立在第 11 条（预设）之上，
  否则会先出现一套无法保存、无法复用的隐式规则。
- **后续可能怎么做**：macro 展开成多条 `ext:` 规则（例如 `source:` → `ext:cpp;cc;cxx;h;hpp;py;js`），
  实现上就是"字符串替换后再解析"。
- **依赖**：预设机制（第 11 条）。
- **影响面**：规则解析层；不影响归档格式。

## 13. 跨平台

- **当前状态**：Filter 与归档格式都只定义 Linux / POSIX 语义：`/` 分隔符、大小写敏感、
  文件名按字节比较、无盘符概念。
- **未来 Windows / macOS 需要处理**：反斜杠分隔符、盘符、大小写不敏感文件系统、
  Unicode 归一化（NFC/NFD）、保留文件名、路径长度限制。
- **为什么 PR #9 不做**：这些是"整套路径模型"的问题，不是 Filter 一个模块能解决的；
  归档格式本身也已经明确拒绝反斜杠与盘符路径。
- **后续可能怎么做**：定义"归档内路径规范化"规则（全部转成 `/` 分隔 + NFC），GUI 层做显示转换。
- **影响面**：路径工具、归档格式校验、Filter 匹配、GUI。

## 14. 时间筛选扩展

- **当前状态**：只支持 `mtime:`（`today` / `yesterday` / `Ndays` / `YYYY-MM-DD` / 日期区间）。
- **未来可能有**：`atime:`、`ctime:`、birth time、带时分秒的 ISO 时间、时区与夏令时处理、
  日历区间（本周 / 本月 / 上一季度）、相对时间（`3months`）。
- **为什么 PR #9 不做**：atime/ctime/birth time 平台差异大，而且 v0.1 归档只保存 mtime，
  多出来的字段在恢复端没有对应物。
- **注意**：当前日期解析使用**本地时区**，测试里用 `TZ=UTC` 固定，避免跨时区出现 flaky。
- **影响面**：Filter 解析与文档；如果扩展到归档元数据，则影响格式版本。

## 15. GUI 高级筛选器

- **当前状态**：PR #9 只做"基础规则编辑"：能加 include / exclude、能删除、能看到列表、非法规则有错误提示。
- **未来可能做**：可视化 rule builder、简单/高级模式切换、preset manager、规则拖拽排序、
  单条规则 enable/disable、导入导出、匹配结果预览（"这条规则会命中哪些文件"）。
- **为什么 PR #9 不做**：先把 C++ Filter 语义与测试固定，UI 是这之上的第二层；
  过早做 builder 会把还没定型的语义固化到界面里。
- **依赖**：规则模型稳定 + 预设机制（第 11 条）。
- **影响面**：Classic GUI 与 Modern GUI；不影响核心与归档格式。

## 16. 其它已延期问题（引用，不重复造文档）

项目里已经存在、与 Filter 无直接关系、但同样属于"以后要处理"的事项，统一引用既有文档，
不在这里复制一遍：

- **TOCTOU 路径竞争**：见 `docs/02_architecture.md` 的"已知可靠性限制与后续改进"；
  当前实现沿用"先检查后写入"，没有 `openat2` / dirfd 沙箱。
- **归档层后续能力**：compression、encryption、完整性校验、去重、多版本，见
  `docs/format/archive_v0.1.md` 的"在备份流水线中的位置"与"已知限制"。
- **GUI 已知限制**：无边框窗口的拖拽 / 边缘缩放需要真实鼠标；任务进行中禁止关窗。
  见 `docs/ui/modern_qml_gui.md` 与 `docs/ui/desktop_gui.md`。

## 附：PR #9 明确不做、但需要测试守住的边界

1. 非法规则必须报错，不能被静默忽略；
2. 非法规则失败时不能留下半成品 `.bak`；
3. 没有规则时行为必须与 PR #8 完全一致；
4. 被 exclude 的目录整棵子树不再扫描（其中的特殊文件也因此不再触发失败）；
5. 没有被排除的特殊文件（symlink / FIFO / socket / 设备）仍然让整次备份失败。
