# 文件系统安全与恢复清理：后续加固 Backlog

> **性质**：当前阶段已知限制 / 后续安全专项；不是 PR #34 的合并阻塞清单，也不是立即实施的指令。  
> **范围**：Linux/POSIX 客户端的备份、增量恢复及临时资源生命周期。  
> **基线**：PR [#34](https://github.com/PlyusWang/backup-project/pull/34) 已修复正常恢复与故障注入下发现的资源认领误删、R-01 失败误成功等真实缺陷，并将确定性认领失败注入加入 canonical gate。

## 1. 已完成的安全基线（不作为待办重做）

- 临时目录的排他认领和所有权状态区分：未创建、已认领、身份不可验证；不能证明身份时保守失败。
- 同名文件 / 硬链接 / 软链接 / FIFO 的标记冲突保护；旧 PID 无标记的对象不清理。
- R-01 多级增量恢复遇到任一失败时不得发布半成品；尾斜杠目标和多级缺失父目录已有回归。
- 构建、sanitizer、GUI/CLI、RED/GREEN、LD_PRELOAD 确定性注入已纳入 PR #34 最终门禁。

上述修复不意味着软件能抵抗同一 UID 下的恶意并发进程。测试所证明的边界与要增强的对抗边界必须区分。

## 2. 未来事项与优先级

| ID | 优先级 | 当前事实与条件 | 后续目标 | 当前阶段 |
| --- | --- | --- | --- | --- |
| FS-01 | **P1：定向审查** | `ExtractDeltaPayload` 的部分失败路径按 pathname `unlink` 自己先前创建的中间文件；若目录项被并发替换，存在检查 / 创建对象和删除对象不一致的条件性风险 | 把文件创建、拥有、失败回滚绑定到可验证对象；先构造确定性替换注入和非本轮文件哨兵 | 延期，尚未证实正常操作下误删 |
| FS-02 | **P1–P2：并发边界** | `RemoveTreeAt` 在 `fstatat(..., AT_SYMLINK_NOFOLLOW)` 后调用 `unlinkat(..., AT_REMOVEDIR)`；`mkdirat` 后的身份探测也不是单一原子操作 | 明确安全保证：不能误递归进入替换对象；无法证明时停止；测试子项被替换、PID 复用、目录重命名等情况 | 已知剩余 TOCTOU，非零风险声明 |
| FS-03 | **P2：威胁模型升级** | 跨 PID 回收的 `*.owner` 标记仍可被**故意且有同 UID 写权限**的进程伪造；魔数、PID 和同 UID 属主并非加密认证或独立权限隔离 | 明确是否需要抵抗同 UID 恶意进程；若需要，设计不可由对手修改的工作区/权限隔离与生命周期机制，不靠“随机文件名就安全” | 当前不把同 UID 恶意进程视作已被彻底隔离 |
| FS-04 | **P2：恢复发布失败语义** | 已存在的空 `destination` 会先被 `rmdir` 再执行 `PublishReplacing`；后一步失败时，原先的空目录可能消失，虽然原有非空用户数据不应被覆盖 | 用故障注入界定“空目录存在性”契约；研究更稳健的提交/回滚策略，不削弱 fail-closed | 已知行为边界，独立于上述三项 |

**优先级升级规则**：如果 FS-01 或 FS-02 在正常单用户、非恶意操作或常见并发环境下被可靠复现为数据误删、覆盖或错误报告成功，立即按 P0/P1 产品缺陷处理，不继续当作普通未来功能。没有复现时，不把“理论窗口存在”写成“已经发生安全事故”。

## 3. 推荐实施顺序与具体方法

### 3.1 FS-01：先做局部最小复现

1. 找到 `ExtractDeltaPayload` 的创建和全部失败分支，记录实际的路径、fd、成功标记及清理条件。
2. 单独构造 LD_PRELOAD/链接器包装等**确定性 syscall 注入**：在成功创建到失败清理之间替换指定中间路径；用独立哨兵记录内容 SHA256、类型、inode、权限及链接数。
3. 要求 RED 真正命中目标 `unlink`，并证明旧实现是否影响不属于当前调用的对象；只看退出码不足以判定。
4. 如果可证实问题，按「本轮创建并持有对象才有清理权限」原则使用父目录 fd 相对操作，必要时保存并验证对象身份；无证明则 fail-closed。
5. GREEN 覆盖失败回滚、无残留、普通 S1/S2/S3 恢复及原子发布；在最终 HEAD 跑 sanitizer 和 canonical gate。

### 3.2 FS-02：精确收紧目录项竞争

1. 逐一标记目录 fd、父 fd、当前目录项名称、身份获取时间与实际 `unlinkat` 时刻。
2. 对「已打开对象但目录项随后替换」进行确定性注入；区分**不跟随软链接递归**与**最终删除了哪个目录项**两种性质。
3. 优先使用受控私有命名空间、fd 相对操作和保守失败；不要仅追加第二次 `lstat`/ `fstatat` 便宣称解决所有 TOCTOU。
4. 明确 Linux 不提供通用的「按已打开目录 fd 原子摘除这个目录项」保证；不承诺不可证明的零竞争窗口。

### 3.3 FS-03：先决定是否真的需要同 UID 对抗

- 明确攻击者是否能对目标的父目录和 `*.owner` 文件写入，是否能运行同 UID 进程。
- 如果需要抵抗这种攻击者，先评估进程权限分离、专用私有工作区、独立安全主体等；不能靠属主检查、PID 或固定魔数建立同 UID 来源证明。
- 检查隔离方案是否改变部署、恢复目标选择、备份格式、安装包或 GUI/CLI 行为；作为独立安全设计任务排期。

### 3.4 FS-04：单独验证目录存在性合同

- 在 `rmdir(destination)` 和最终发布之间精确注入失败，比较进入前后的空目标目录及其父目录。
- 如需修改，先形成明确、可测试的对外行为契约，不要在 FS-01 的小修中顺手重构全项目发布原语。

## 4. 每项完成的证据标准

- 记录 **威胁模型与是否可复现**，不得把条件风险写成既成事故。
- 旧版 RED 与修复版 GREEN 使用一致的产品级断言、受控隔离目录和明确的注入命中证据；`SKIP` 不算 `PASS`。
- 重点验证哨兵内容、对象身份和权限、正确失败返回、原目标与非本轮对象不变。
- 对真实改动执行 C++ 单元/集成、ASan/UBSan、CLI/GUI 受影响路径和最终提交的 canonical gate；禁止把 ECS 上的旧二进制当作新代码测试。
- 每项保留独立证据和小范围提交；不自动重部署 ECS、不修改正式证书/密钥/数据库。
- 有意接受的残余窗口在代码或运维说明中说明边界，不宣称绝对无 TOCTOU。
