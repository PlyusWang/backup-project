# 数据备份与恢复系统文档修改建议

本文针对当前的 `user.docx` 和《数据备份与恢复系统——功能用例描述》进行检查，并结合项目现有的总体用例图、组件图、类图、备份时序图和恢复时序图提出修改建议。

总体上，现有文档的功能覆盖比较完整，UC-01～UC-07 中的目标、前置条件、成功/失败状态、基本流程和异常流程均可以保留。主要需要调整的是 UML 建模语义、系统内部模块与外部参与者的区分，以及文档中“当前已实现功能”和“后续计划功能”的边界。

## 1. 总体用例图

建议以现有 StarUML 总体用例图的建模方式为基础修改，而不是重新设计一套完全不同的关系。

当前 Sprint 已经实际实现的用户级用例主要是：

- 备份目录
- 恢复备份
- 查看命令行帮助

这三个用例都可以直接通过 association 与“本地用户”连接。

如果总体用例图希望描述最终完整系统，也可以继续加入：

- 配置文件过滤
- 设置备份密码
- 配置定时备份
- 查看备份状态
- 查看备份历史

但应注意区分“已实现”和“规划功能”，例如在图注或正文中注明这些功能属于后续 Sprint。

不建议把以下内容全部画成独立用例：

- 扫描源目录
- 收集文件元数据
- 创建备份归档
- 压缩
- 加密
- 存储
- 解密
- 解压
- 解包

这些主要是系统内部的处理步骤，并不是用户直接发起、具有独立用户目标的用例。它们更适合出现在事件流、组件图和时序图中。

另外，不需要为了体现 UML 的 `include`、`extend`、generalization 等关系而强行加入关系。只有语义确实成立时才使用。

## 2. `include` 和 `extend` 关系需要重新检查

当前文档把“扫描源目录、筛选文件、收集元数据、打包、压缩、加密、存储”等全部列为“数据备份”的包含用例。

从实现流程角度这样理解没有问题，但从 UML 用例建模角度并不理想。

这些步骤更像：

> 数据备份内部执行流程

而不是：

> 用户可以单独理解和发起的完整用例

因此建议：

- 在用例表中的“包含用例”一栏适当减少或取消这些内部步骤；
- 把它们完整保留在 UC-01 的“基本流程”中；
- 在系统设计阶段通过组件图和备份时序图表示这些步骤由哪些模块完成。

恢复部分同理。

当前“定时备份”和“实时备份”也不建议简单地画成“数据备份”的 `extend`。

更准确的理解是：

> 定时调度或文件事件负责触发一次备份，而真正执行备份工作的仍然是统一的 BackupEngine。

这一点在后续时序图或组件图中表达会比强行使用 `extend` 更清楚。

## 3. Actor 需要修正

UC-06 中把“系统定时调度器”作为参与者，UC-07 中把“文件监控模块”作为参与者，这一点建议修改。

因为整个系统边界已经定义为“数据备份与恢复系统”，那么：

- Scheduler
- Watcher
- FileSystem
- BackupEngine

这些都属于系统内部模块，不应再作为系统外部 Actor。

UC-06 可以改为：

- 参与者：本地用户
- 触发器：到达用户预先配置的执行时间

UC-07 可以改为：

- 参与者：本地用户
- 触发器：被监听目录发生文件创建、修改、删除或移动事件

这里“定时器”和“文件监控模块”属于系统内部机制，应放在组件图或时序图中表达。

## 4. UC-01 数据备份

UC-01 整体内容可以保留，基本流程写得比较完整。

建议主要修改两点。

第一，当前项目的 Sprint 1 实际只完成了：

> 普通文件和目录的递归复制备份

因此“元数据、归档、压缩、加密”等内容目前应明确属于完整系统规划，而不是已经实现的行为。

第二，建议将基本流程分成逻辑阶段，而不是把所有内部实现步骤都提升为独立用例：

> 检查参数 → 扫描文件树 → 根据配置处理文件 → 写入备份存储 → 返回结果

以后真正实现过滤、归档、压缩和加密后，可以继续细化。

当前列出的路径不存在、权限不足、空间不足、写入失败等异常流程可以保留，这些内容以后也可以直接转化为测试用例。

## 5. UC-02 数据恢复

UC-02 的整体结构也可以保留。

建议恢复流程与现有恢复时序图保持一致，即：

> 用户 → CLI / UI → RestoreEngine → FileSystem / 后续归档模块 → Linux 文件系统

当前 Sprint 1 实际实现的是从：

`repository/data`

恢复目录树到目标目录。

因此当前正式文档中需要区分：

### 当前实现

读取备份目录并递归恢复普通文件和目录。

### 后续完整流程

读取备份 → 解密 → 解压 → 解包 → 重建目录和文件 → 恢复元数据。

这样文档与代码状态能够对应，不会出现文档已经描述完整归档格式，但代码实际上还是目录树复制的情况。

## 6. UC-03 配置文件过滤

该用例本身合理，可以保留。

路径、文件名、文件类型、时间、尺寸、用户和用户组等条件也与课程功能要求基本一致。

不过建议不要现在就写死具体过滤语法。

保留：

> 过滤语法在系统设计阶段确定

是合适的。

以后真正实现 FilterEngine 后，再补：

- include / exclude 的优先级
- 多条规则冲突处理
- 路径匹配规则
- 大小和时间的单位
- UID / GID 或用户名匹配方式

即可。

## 7. UC-04 设置备份密码

该用例可以保留，但“扩展用例：数据备份；数据恢复”建议删除。

“设置备份密码”本身是一个独立配置行为，它会影响后续：

- 备份时的加密
- 恢复时的解密

但这不意味着“数据备份”和“数据恢复”就是它的 `extend` 用例。

建议在“语境目标”或“补充规格说明”中说明：

> 密码配置供后续备份加密和恢复解密模块使用。

这样比强行建立 UML `extend` 关系更准确。

## 8. UC-05 配置定时备份

这个用例可以保留，而且属于比较典型的用户级用例。

用户确实可以主动：

- 创建任务
- 修改任务
- 设置周期
- 选择源目录
- 选择目标位置
- 启用或停用任务

因此它非常适合出现在总体用例图中。

“每 N 分钟、每小时、每天、每周”的计划也可以暂时保留，等 Scheduler 实现后再根据实际功能修订。

## 9. UC-06 定时备份

建议不要把“定时备份”过度描述成一个由“系统定时调度器”参与的独立用户用例。

从系统设计角度，它更像：

> Scheduler 到时 → 调用 BackupEngine → 执行一次普通数据备份

因此文档中可以保留 UC-06 作为自动化场景说明，但最好明确：

> 定时备份复用普通数据备份核心，而不是另一套备份实现。

这样也能够和之后的组件图、类图保持一致。

## 10. UC-07 实时备份

实时备份同样建议保留，但需要调整参与者描述。

核心设计应表达为：

> Watcher 使用 Linux `inotify` 监听目录变化 → 检测事件 → 根据策略触发 BackupEngine。

其中 Watcher 是系统内部组件，而不是 Actor。

另外以后实现时还需要补充几个关键策略，目前文档不必展开，但最终设计中需要明确：

- 连续修改事件是否合并
- 删除事件如何处理
- rename / move 如何处理
- 短时间大量文件变化如何避免重复备份
- 程序退出后重新启动如何恢复监听状态

## 11. “功能之间的整体关系”图

当前文档中的功能关系图可以保留，但建议不要把它作为 UML 图。

建议名称改成：

> 数据备份与恢复系统功能分解图

或者：

> 数据备份与恢复处理流程示意图

其中：

> 扫描 → 过滤 → 元数据 → 打包 → 压缩 → 加密 → 存储

以及：

> 读取 → 解密 → 解压 → 解包 → 文件与元数据恢复

作为功能处理链是合理的。

以后组件图负责回答：

> 谁来做这些事情？

时序图负责回答：

> 这些模块按照什么顺序交互？

功能分解图只需要回答：

> 整个系统有哪些处理阶段？

三种图不要混在一起。

## 12. 甘特图

建议使用项目现有的甘特图版本作为正式版本。

时间轴最好直接对应课程的 10 次实验课 / Sprint，而不是使用连续的抽象数字。

整体阶段可以保持：

> Sprint 1 基础 CLI  
> → 本地文件功能扩展  
> → 过滤 / 元数据 / 归档 / 压缩 / 加密  
> → GUI  
> → 定时 / 实时备份  
> → 网络功能  
> → 系统测试  
> → 文档整理与答辩

甘特图只维护一份持续更新的源文件即可，不需要每周复制一个新的甘特图。Git 历史本身已经能够保存每个阶段的变化。

## 13. 与现有 UML 图的统一

后续文档应尽量保持以下对应关系：

### 总体用例图

回答：

> 用户能够使用系统完成什么？

不要塞入过多内部实现步骤。

### 组件图

回答：

> 系统由哪些模块组成？

例如：

- CLI / Web UI
- BackupEngine
- RestoreEngine
- FileSystem
- FilterEngine
- Archive
- Compression
- Crypto
- Scheduler
- Watcher
- StorageBackend

### 类图

回答：

> C++ 中有哪些核心类，它们之间是什么关系？

应尽量使用真实代码中的类名，而不是为了画图创造不存在的类。

### 时序图

回答：

> 一次备份或恢复过程中，各对象按照什么顺序调用？

例如当前备份流程保持：

> 用户 → `backupctl` → `BackupEngine` → `FileSystem` → Linux/POSIX 文件系统

以后加入压缩、加密等模块后，再在这个基础上扩展。

## 14. 最终建议

当前两份文档不需要推翻重做。

建议保留：

- UC-01～UC-07 的主体文字
- 前置条件
- 成功与失败状态
- 基本流程
- 异常流程
- 功能分解思路
- 甘特图中的整体开发阶段

重点修改：

1. 删除或减少把系统内部处理步骤当作独立 UML 用例的情况；
2. 修正定时调度器、文件监控模块作为 Actor 的问题；
3. 不强行使用 `include` 和 `extend`；
4. 明确区分当前 Sprint 已实现功能和完整项目规划；
5. 总体用例图、组件图、类图和时序图分别承担不同层次的表达任务；
6. 后续随着真实代码变化同步更新文档，不提前写出尚未确定的实现细节。

这样修改后，两份文档基本可以继续作为需求分析和后续系统设计的基础，不需要重新从零编写。
